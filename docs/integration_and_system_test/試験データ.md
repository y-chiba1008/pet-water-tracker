# 試験データ

日時はすべて **試験実施日を基準日 D** とした相対指定。時刻は JST（`HH:mm`）。

アプリの日別集計は「ブラウザのローカル日付」に載せる。水皿記録は **終了日時の日付**、個別記録は **記録日時の日付**。

---

## 1. アカウント

| ID | 役割 | 用意するもの |
|---|---|---|
| U-OK | 許可ユーザー | `scripts/seed-users.config.json` に載せた Google アカウント（1名で実施） |
| U-NG | 未登録ユーザー | config に **載せていない** 別の Google アカウント |

- 2名共有の試験はしない。U-OK は config の何件目でもよいが、実施中は同じアカウントを使い続ける
- U-NG の確認はシークレットウィンドウか、Google アカウントを切り替えて行う
- `pnpm seed-users` は Admin API で `auth.users` / `public.users` を作るだけ。水皿・記録は作らない

---

## 2. 日時記号

| 記号 | 意味 | 例（D = 2026-09-23 のとき） |
|---|---|---|
| D | 試験実施日（JST の暦日） | 2026-09-23 |
| D-1, D-2, … | D の n 日前 | D-1 = 2026-09-22 |
| D-29 | グラフ期間の先頭（今日を含めて 30 日） | 2026-08-25 |
| D-30 | グラフ期間の直前（グラフに載せない） | 2026-08-24 |
| 前月最終日 | `D` の属する月の 1 日の前日 | 2026-08-31 |
| いま | 操作時点の現在時刻（分精度） | — |

折れ線グラフの期間は実装どおり **D-29 0:00 〜 D 23:59:59.999**（今日を含む直近 30 日）。

## 3. セット B で UI から作るデータ

セット B 開始時は水皿ゼロ。シナリオの順に次を登録する。

### 水皿

| ID | 名前 | 用途 |
|---|---|---|
| B-LIVING | リビング | 開始・交換・当日集計 |
| B-BED | 寝室 | 水皿ごとの独立、片付け、削除 |

名前バリデーション用（保存しない）:

| 入力 | 期待 |
|---|---|
| （空／空白のみ） | 「水皿の名前を入力してください。」 |
| 40 文字ちょうど | 保存できる |
| 41 文字 | 「40文字以内で入力してください。」 |

40 文字の例: `あ` を 40 回。41 文字はその +1。

### 記録（シナリオ REC-* で投入。時刻は実施時に「いま」または指定の相対）

| ID | 操作 | 水皿 | 日時 | 容量 | 飲水量 | 集計日 |
|---|---|---|---|---|---|---|
| UI-BR-1 | 給水開始 | リビング | いま | 開始 200ml | （未確定） | 載らない |
| UI-BR-2 | 交換（終了+開始） | リビング | いま | 残り 50ml / 新しい 200ml | 150ml | D |
| UI-IR-1 | 個別給水 | — | いま | 10ml | 10ml | D |
| UI-BR-3 | 給水開始→片付け | 寝室 | 開始は D の少し前、終了はいま | 開始 150ml / 残り 100ml | 50ml | D |

UI-BR-2 のあと、リビングは **設置中（新しい 200ml）** のまま。この進行中分はホームに加算しない。

**セット B 終了時点の「今日の合計」（UI-BR-2 + UI-IR-1 + UI-BR-3）:** 150 + 10 + 50 = **210ml**  
（片付け前にホームを見るケースでは 160ml。シナリオ本文の時点に従う）

## 4. セット C（`seed.sql`）

ユーザー作成後に投入する。水皿名は UI 作成分と区別するため接頭辞 `集計用` を付ける。

### 水皿

| ID | 名前 | 状態 |
|---|---|---|
| C-LIVING | 集計用リビング | 有効。完了 2 件 + 進行中 1 件 |
| C-BED | 集計用寝室 | 有効。完了 1 件 |

### 水皿記録

| ID | 水皿 | 開始（JST） | 開始容量 | 終了（JST） | 終了容量 | 飲水量 | 集計日 |
|---|---|---|---|---|---|---|---|
| TD-BR-01 | 集計用リビング | D-2 20:00 | 200 | D-1 08:00 | 80 | 120 | D-1 |
| TD-BR-02 | 集計用リビング | D-1 08:00 | 200 | D 08:00 | 50 | 150 | **D**（日付またぎ。全量を終了日へ） |
| TD-BR-03 | 集計用リビング | D 08:00 | 200 | （なし） | （なし） | 未確定 | **載せない** |
| TD-BR-04 | 集計用寝室 | D-1 10:00 | 150 | D-1 18:00 | 100 | 50 | D-1 |

### 個別記録

| ID | 記録日時（JST） | 量 | 集計日 | ねらい |
|---|---|---|---|---|
| TD-IR-01 | D 12:00 | 10 | D | 当日の水皿との合算 |
| TD-IR-02 | D-1 12:00 | 20 | D-1 | 前日合算 |
| TD-IR-03 | D-29 12:00 | 30 | D-29 | グラフに **含める** |
| TD-IR-04 | D-30 12:00 | 40 | D-30 | グラフに **含めない** |
| TD-IR-05 | 前月最終日 12:00 | 70 | 前月最終日 | カレンダー前月 |

### 期待値（セット C・投入直後・追加操作なし）

日別合計:

| 日付 | 内訳 | 合計 |
|---|---|---|
| D | TD-BR-02 150 + TD-IR-01 10 | **160ml** |
| D-1 | 120 + 50 + 20 | **190ml** |
| D-29 | TD-IR-03 | **30ml** |
| D-30 | TD-IR-04 | **40ml**（グラフ対象外） |
| 前月最終日 | TD-IR-05 | **70ml**（D-29 や D-30 と同一日なら合算。下の注意） |

**今日の合計:** 160ml  
**前回の記録:** 個別 TD-IR-01（D 12:00）が水皿終了（D 08:00）より新しいので、カードは `前回の記録 12:00`

**折れ線グラフ:**

- 先頭の日付ラベルは D-29（例: `8/25`）、末尾は `今日`
- D は 160、D-1 は 190、D-29 は 30
- D-30 の 40ml は系列に出さない
- 最高: 上記のうちグラフ期間に入る値の最大（通常は D-1 の 190ml）
- 最低: 期間内で 0 でない日の最小（記録がない日の 0 は最低に使わない）

**今月の 1 日平均:**

```
平均 = round( 当月1日〜D の飲水量合計 / その日数 )
記録日数 = 同じ期間で合計がマップに載っている日の数
```

日数は「D の日」そのもの（例: 23 日なら 23 で割る）。記録がない日も分母に含む。

D が 2026-09-23 で、D-29・D-30・前月最終日がすべて 8 月のとき:

- 当月の記録日: D-1（190）と D（160）のみ
- 合計 350、日数 23、平均 `round(350 / 23) = 15`
- 「計 2日間 記録済み」

実施日が月をまたぐ位置にある場合は、下の手順で数値を再計算する。

### D-29 / D-30 と前月最終日が重なるとき

同一ローカル日に複数レコードがあると **合算** する。

例: D = 2026-08-31 なら前月最終日は 7/31 で重ならない。  
D = 2026-09-30 なら D-29 = 8/31 で、前月最終日 8/31 と TD-IR-03 が同一日 → カレンダー 8/31 は 30 + 70 = **100ml**。グラフにも 100ml で出る。

実施時に基準日 D をメモし、重なりがあれば期待値を書き換える。

## 5. セット C の投入手順

```bash
pnpm exec supabase db reset
pnpm seed-users

DB_URL="$(pnpm exec supabase status -o env | grep '^DB_URL=' | cut -d= -f2- | tr -d '"')"
psql "$DB_URL" -f docs/integration_and_system_test/seed.sql
```

`psql` はスーパーユーザー接続のため RLS をバイパスする。`DB_URL` は `supabase start` 済みであること。

投入確認の例:

```sql
select name, is_active from public.bowls order by created_at;
select b.name, r.start_time, r.start_amount_ml, r.end_time, r.end_amount_ml
from public.bowl_records r
join public.bowls b on b.id = r.bowl_id
order by r.start_time;
select recorded_at, amount_ml from public.individual_records order by recorded_at;
```

`public.users` が空だと SQL はエラーで止まる。

## 6. 容量の境界（バリデーション用。DB には残さない）

| 画面 | 入力 | 期待メッセージ |
|---|---|---|
| 水皿交換・新しい容量 / 残った容量 | 未入力 | 「新しい容量を入力してください。」 / 「残った容量を入力してください。」 |
| 同上 | 0 | 受付（0ml 以上） |
| 同上 | 5000 | 受付 |
| 同上 | 5001 | 「5000ml以下で入力してください。」 |
| 同上 | 小数（1.5 など） | 「整数で入力してください。」 |
| 水皿交換・残った容量 | 開始より大きい | 見込みが警告色。「終了容量は開始容量以下にしてください。」保存不可 |
| 個別給水 | 未入力 | 「飲水量を入力してください。」 |
| 個別給水 | 0 | 「1ml以上で入力してください。」 |
| 個別給水 | 500 | 受付 |
| 個別給水 | 501 | 「500ml以下で入力してください。」 |
| 日時 | 空 | 「日時を入力してください。」 |
| 日時 | いまより未来 | 「現在時刻以前の日時を入力してください。」 |
| 水皿交換 | 前回記録より前 | 「前回の記録時刻以降の日時を入力してください。」 |

## 7. 通信失敗の起こし方（全 ERR 共通）

アプリは `http://localhost:3000`、API は `http://127.0.0.1:54321`。失敗を安定して出すには **API だけ止める**。

### 取得失敗（画面を開いた状態でデータが取れない）

1. Chrome DevTools（F12）→ **Network**
2. フィルタに `54321` を入れると API だけ見やすい
3. 画面をリロードする直前に、DevTools 右上のスロットリングを **Offline** にする  
   （または Network で `rest/v1` を右クリック → Block request URL）
4. 対象画面を再読み込みする（アドレスバー Enter、またはフッターで同じ画面を押し直す）
5. 期待メッセージと「再読み込み」ボタンを確認する
6. スロットリングを **No throttling** に戻す（ブロックしていれば解除する）
7. 「再読み込み」を押し、データが表示されることを確認する

Offline のままだと「再読み込み」も失敗する。復帰確認の前に必ず Online に戻す。

### 保存・削除失敗（フォームは埋まっている状態）

1. 対象フォームを **送信できる状態まで** 入力する（バリデーションを先に通す）
2. DevTools を **Offline** にする（送信前）
3. 保存／削除する を押す
4. 「保存に失敗しました。もう一度お試しください。」または削除なら「削除に失敗しました。もう一度お試しください。」
5. Online に戻し、同じ操作をやり直して成功することを確認する（任意だが ERR の最後で実施）

### ログインボタン押下時の失敗

1. ログアウト済みの `/login` を開く
2. DevTools を Offline にする
3. 「Google でログイン」を押す
4. 「ログインに失敗しました。もう一度お試しください。」

OAuth 画面に遷移してから失敗させる必要はない（遷移前の `signInWithOAuth` 失敗を見る）。

### 使わない方法

- `supabase db reset`（データが消える。失敗再現の手段にしない）
- `supabase stop`（Auth ごと落ち、復帰が重い。最終手段のみ）
